# 外部連携用トークン 共通仕様（他アプリへの展開用）

AIアシスタント（Muse のカスタムコネクタなど）や他のサービスから、家庭用アプリの API を安全に呼ぶための仕組みの共通仕様。
StockHome で実装・本番運用したもの（notice 028・029、2026-11-26）を、他のアプリの API にも同じ形で入れられるよう一般化した。

- 参考実装（StockHome）: `apps/api/src/plugins/auth.ts`、`apps/api/src/services/apiTokens.ts`、`apps/api/src/services/apiTokenAlerts.ts`、
  `apps/api/src/routes/apiTokens.ts`、`apps/mobile/src/screens/settings/ApiTokensScreen.tsx`、migration `20261126120000_add_api_tokens`・`20261126180000_add_api_token_last_alerted_at`
- StockHome 固有の利用者向け説明: `docs/EXTERNAL_API.md`

## 1. 目的と前提

| 解決したいこと | この仕様での答え |
|---|---|
| ログイン用トークン（JWT など）は期限があり、連携先で定期的に入れ直す必要がある | 期限なし・取り消すまで有効な、連携専用のトークンを別に用意する |
| ログイン用トークンは利用者の全権限を持ち、連携先からの書き込みを API 側で止められない | トークンごとに「読み取りだけ／書き込みも可」を利用者がアプリで切り替える。既定は読み取りだけ |
| 連携先に個人情報（メールアドレス等）を渡したくない | 個人情報を返す API は、トークンでは参照も含めて使えないようにする |
| 悪用に気づけない | 拒否を本人へ通知し、ログに誰の・どのトークンかを残す |

前提: 利用者ごとのログイン（JWT 等）があり、データは世帯（household）などの単位で分かれていること。連携先は HTTPS で
`Authorization: Bearer <トークン>` を付けて呼べること。

## 2. トークン

- 形式: アプリ固有の目印 ＋ 32バイトの乱数（base64url）。例 `shk_` ＋ 43文字。**目印はアプリごとに変える**（例 `hma_`）。
  目印でログイン用トークンと見分ける（JWT は `eyJ` で始まるので衝突しない）
- **発行した本人として動く**。その人の世帯のデータだけを扱い、書き込みはその人の操作として記録される
- 期限なし。取り消すまで有効。取り消しは即時
- 発行時に1度だけ本体を表示する。サーバーは本体を保存しない
- 1人あたりの有効なトークン数に上限を設ける（StockHome は10個）
- 「再発行」はない。入れ替えは「新しく発行 → 連携先に登録 → 古い方を取り消す」の順

## 3. 保存（DB）

テーブル `api_tokens`（列名は StockHome のもの）:

| 列 | 内容 |
|---|---|
| `id` | 主キー |
| `household_id`・`user_id` | 発行者と世帯（外部キー、削除時は連鎖削除） |
| `name` | 利用者が付ける名前（例「Museきなこ」）。50文字まで |
| `token_hash` | トークン本体の SHA-256（16進64文字）。一意 |
| `token_prefix` | 一覧で見分けるための先頭部分（目印＋6文字）。これだけでは認証に使えない |
| `allow_write` | 書き込みの許可。既定 false |
| `last_used_at` | 最終利用日時。リクエストのたびに書かず、前回から10分以上空いたときだけ更新 |
| `last_alerted_at` | 拒否を本人へ通知した日時（通知の間引き用） |
| `revoked_at` | 取り消し日時。null なら有効。行は消さない（取り消し後の利用を検知するため） |

- ハッシュは SHA-256 で十分（本体が推測できない長さの乱数のため、パスワード用の遅いハッシュは不要）
- backup にはハッシュしか入らず、backup からトークンとして使うことはできない

## 4. 認証の流れ

既存の認証フック（StockHome は Fastify の `authenticate` preHandler）の先頭で分岐する。

1. `Authorization: Bearer <値>` の値が目印で始まらなければ、従来のログイン用トークンとして検証する（従来の挙動は変えない）
2. 目印で始まれば、SHA-256 で `api_tokens` を引き、次の順に判定する

| 順 | 判定 | 応答 | 本人への通知 |
|---|---|---|---|
| 1 | 該当なし | 401 | しない（誰のものか分からない） |
| 2 | 取り消し済み | 401 | する（`revoked`） |
| 3 | 発行者が世帯のメンバーでない | 403 | しない |
| 4 | 発行者のアカウントが無効 | 403 | しない |
| 5 | トークンでは使えない API（下記 5.） | 403 | する（`denied_route`） |
| 6 | 書き込み未許可のトークンで GET・HEAD 以外 | 403 | する（`write_not_allowed`） |
| 7 | 通過 | — | — |

- 通過したら、リクエストの認証情報を「発行者の userId・世帯・役割 ＋ トークンID」にする。以降の各 API は従来どおり世帯で絞り込む
- 拒否はすべて認証の段階で返し、各 API の処理には到達させない
- 応答の文言は利用者に伝わる言葉にする（例「このトークンは読み取り専用です。アプリの『外部連携』で書き込みを許可できます」）。
  連携先の AI がそのまま利用者に伝えられる

## 5. トークンでは使えない API（拒否リスト）

**書き込みを許可していても、参照も含めて拒否する。** 判定は route のパターン（例 `/api/users/:id`）の前方一致で行う。
新しいアプリに入れるときは、次の分類ごとに該当する API を洗い出す。

| 分類 | 理由 | StockHome での該当 |
|---|---|---|
| トークン管理 | トークンから新しいトークンを作ったり、自分の許可を広げたりさせない | `/api/api-tokens` |
| ログイン・アカウント | パスワード変更などで乗っ取りに使わせない | `/api/auth/*` |
| 個人情報を返すもの | メールアドレス・端末ID・メール本文などを連携先に渡さない | `/api/users`（メールアドレス）、`/api/push-devices`、`/api/import-candidates`・`/api/reflections`（取込メールの差出人・件名・本文の一部） |
| **世帯を越える処理を起動するもの** | 管理者のトークンから、他の世帯に影響する処理を動かさせない | `/api/dashboard/run-batch`（夜間バッチ内の通知の配信結果確認が世帯を限定しない） |

- パスワードは、どの API も返さないこと（DB にもハッシュのみ）を前提として確認しておく
- 「個人情報」は**応答に含まれる項目**で判断する。名前が無害そうな API でも、応答の中にメールアドレスや外部サービスの本文が入っていないか確認する
- 「世帯を越える処理」は、route の中で世帯の条件なしに DB や外部サービスを触る関数を呼んでいないかで洗い出す（StockHome の VPS レビューで差し戻された点）

## 6. 管理 API とアプリの画面

管理 API（ログイン用トークンのみ。外部連携用トークンでは拒否リストにより使えない）:

| API | 内容 |
|---|---|
| `GET /api/api-tokens` | 一覧。メンバーは自分の分、管理者は世帯全員の分。取り消し済みは出さない |
| `POST /api/api-tokens` | 発行（`name`、`allowWrite` 既定 false）。発行は本人の分のみ。応答でだけ本体を返す |
| `PATCH /api/api-tokens/:id` | 書き込み許可の切り替え（本人、または管理者） |
| `DELETE /api/api-tokens/:id` | 取り消し（本人、または管理者）。204 |

一覧の項目: `id`・`name`・`tokenPrefix`・`allowWrite`・`lastUsedAt`・`createdAt`・`owner {id, name}`・`isMine`。ハッシュや通知日時は返さない。

アプリの画面（設定 → 外部連携）:
- 発行: 名前を入れる → トークンを1度だけ表示し「コピーする」。閉じる前に「二度と表示できません」と確認
- 一覧: 名前・持ち主・先頭部分・最後に使われた日時・書き込みのスイッチ・取り消し
- 書き込みを ON にするときは、何ができるようになるかを示して確認する
- 家族それぞれが自分のアプリから発行する（他人の分は発行できない）。管理者は全員の分を切り替え・取り消しできる

## 7. 悪用の検知

### 本人への通知

- 正しく使う連携先は拒否されない、という前提で、**拒否そのものを想定外の使われ方の合図**とする
- 4.の表で「する」になっている拒否で、発行者の端末へプッシュ通知する。同じトークンにつき**24時間に1回まで**
- 文面の例: 「外部連携のトークンで拒否された操作がありました」「『Museきなこ』で、読み取り専用なのに書き込みが試されました。
  心当たりがなければ、アプリの『せってい → 外部連携』で取り消してください」
- **送る相手を通知の直前に確認する**: 発行者が今も有効で、トークンの世帯のメンバーであること。満たさなければ送らない。
  取り消し済みの判定は所属・有効性の確認より前にあるため、ここで確かめないと、無効化した人や世帯から外れた人に通知が届き得る（StockHome の VPS レビューで差し戻された点）
- 通知済みの印（`last_alerted_at`）は**送信前に**条件付き更新（前回から24時間以上空いていれば更新）で取る。同時に何件拒否されても通知は1回になる。
  送る相手がいないときは印を付けない
- 通知は応答を待たせないよう非同期にし、失敗はログに残す

### ログ

| event | 出すとき | 主な項目 |
|---|---|---|
| `http_request`（既存に項目追加） | 全リクエスト | 認証済みなら `user_id`・`auth_kind`（`jwt`／`api_token`）・`api_token_id` |
| `api_token_denied` | トークンでの拒否すべて | `reason`（`unknown`・`revoked`・`no_membership`・`user_inactive`・`denied_route`・`write_not_allowed`）・`api_token_id`（分かる場合）・`method`・`route` |
| `api_token_alert_sent` | 1台以上で受理された | `push_targeted`・`push_accepted`・`push_failed` |
| `api_token_alert_no_target` | 送る相手・端末がない | `cause`: `owner_inactive`・`owner_not_member`・`no_active_device` |
| `api_token_alert_failed` | 送る先はあったが受理0台、または例外 | `cause`: `push_not_accepted`・`exception` |

- **結果ごとに event を分ける**。送れなかったのに「sent」と記録しない（StockHome の VPS レビューで差し戻された点）。一部の端末だけ失敗したときは sent とし、失敗数を残す
- トークン本体・メールアドレスはログに出さない（テストでログ全体に含まれないことを確認する）

## 8. テストの観点（回帰テストのチェックリスト）

- [ ] 発行で目印付きの本体が返り、DB にはハッシュだけが入る
- [ ] 読み取り専用のトークンで GET は通り、書き込みは 403。許可に切り替えると通る
- [ ] 書き込み許可のトークンでも、拒否リストの API はすべて 403（参照も含む）
- [ ] 世帯を越える処理を起動する API は、書き込み許可の**管理者の**トークンでも 403 で、処理（外部への問い合わせ・他世帯のデータ変更）が一切走らない
- [ ] 取り消し・存在しない・発行者の無効化・世帯から外れた場合の拒否
- [ ] 一覧・切り替え・取り消しの範囲（メンバーは自分、管理者は全員。他人の分は 404）
- [ ] 書き込みは発行者の世帯に対して行われる
- [ ] 通知: 送れた／一部失敗／端末なし／全件失敗／外部送信自体の失敗／24時間以内の2回目、それぞれの戻り値と event
- [ ] 通知: 発行者の無効化・世帯から外れた場合は、端末が残っていても送らない（HTTP 経由と直接呼び出しの両方）
- [ ] ログ: `auth_kind`・`api_token_id`・`user_id`、`api_token_denied` の理由、トークン本体が含まれないこと
- [ ] **テストが効いていることの確認**: 修正（拒否・通知・間引き・発行者の確認）を一時的に外すとテストが失敗すること。
  未コミットの修正を消さないよう、先にコミットしてから試し、コミットの状態へ戻す

## 9. 導入の手順と手続き（VPS で動くアプリの場合）

1. API: 3.のテーブルと migration、4.の認証分岐、5.の拒否リスト（アプリごとに洗い出す）、6.の管理 API、7.の通知とログ
2. 入力の型（Zod など）は共有パッケージから定義する
3. テスト: 8.のチェックリスト。使い捨ての DB で全件実行し、本番と同じ作り方で image を build して、空の DB で結合確認する
4. 届け出: 認証経路の追加と migration を含むため **L3**。notice を出し、VPS 管理のレビュー → 本番反映の承認 → 反映 → read-only 確認
5. アプリの画面は API の反映後に配信する（client release）
6. 反映後、利用者の了承を得て、読み取り専用トークンで書き込みを1回試し、拒否と通知の到達を確認する（データは変わらない。そのトークンは24時間通知が止まる）
7. 連携先へ渡すもの: ホスト名、`Authorization: Bearer` の使い方、使ってよい API と応答の項目、使えない API、エラー時の案内文。トークン本体はチャットに貼らず、連携先の安全な入力欄に利用者が登録する

## 10. 既知の制約

- 権限は「読み取りだけ／書き込みも可」の2段階。API ごとの細かい許可は持たない（必要になったら拒否リストを許可リストに変える）
- 通知はプッシュ通知を有効にした端末にしか届かない。発行者が無効・世帯外のときは誰にも通知しない（ログのみ）
- 通知の印は送信前に付けるため、外部への送信に失敗しても24時間は再送しない
- ログイン用トークンでの管理者操作（StockHome の夜間バッチの手動実行など）が世帯を越える場合、それはトークンの仕組みとは別に直す必要がある
